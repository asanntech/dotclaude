# Address Review Skill

PR のレビュー指摘への対応を **1 周ぶん** 行う。直す指摘は毎回ユーザーが選ぶ。このスキルが自分で次の周を始めることはない。

レビューと修正を同じモデルが行うため、完全に自動でループさせると、間違った指摘や実現できない指摘をそのまま直したり、任意の指摘を直すたびに新しい指摘が出て止まらなくなったりする。そのため、判断はユーザーに任せ、それ以外の作業をまとめて行う。

引数: PR 番号または PR の URL（必須）。GitHub との連携は `gh` CLI に統一する（MCP GitHub ツールは使わない）。

## 手順

### 1. 指摘を集める

```bash
# PR の情報（HEAD のコミットとブランチ）
gh pr view {pr_number} --repo {owner}/{repo} --json number,headRefName,headRefOid,state

# レビューの一覧。自分の Pending レビューもここに出る
gh api repos/{owner}/{repo}/pulls/{pull_number}/reviews --jq '.[] | {id, state, commit_id, user: .user.login, body}'

# 指摘のスレッド（返信を含む）。Pending レビューのコメントは reviews/{review_id}/comments で取る
gh api repos/{owner}/{repo}/pulls/{pull_number}/comments --jq '.[] | {id, in_reply_to_id, path, line, user: .user.login, body}'
gh api repos/{owner}/{repo}/pulls/{pull_number}/reviews/{review_id}/comments --jq '.[] | {id, path, line, body}'
```

- 対象は、まだ対応していない指摘。次のものは除外する:
  - スレッドに判断（対応しない、別の PR で対応する など）が返信されている指摘
  - 後のコミットで、すでに直っている指摘
- 作業ブランチが PR のブランチで、作業ツリーがクリーンなことを確かめる。違えば止めて報告する

### 2. 指摘を確かめる

直す前に、指摘ごとに問題が本当に起きるかを確かめる（再現するコマンドを実行する、該当するコードやライブラリの挙動を読む など）。

- 指摘が誤っている、または前提が違う場合は、その根拠を手順 3 で示す
- 実現できない、または指摘のとおりに直すと別の問題が起きる場合も、手順 3 で示す

### 3. 直す指摘を選んでもらう

指摘ごとに、手順 2 の結果と自分の見解（直すべきか、直すならどう直すか、別の時期に回すべきか）を添えて提示する。そのうえで AskUserQuestion で選んでもらう。選択肢は「直す / 直さない / 後で直す」を基本にする。

- 自分の判断で、指摘を直す・直さないを決めない
- ユーザーが選んだ時点で、選ばれた指摘の修正、コミット、push、再レビューの開始まで承認されたものとする

### 4. 1 件ずつ直す

選ばれた指摘を 1 件ずつ、次のように直す。

- **振る舞いが変わる修正**: 先に失敗するテストを書き、意図した理由で失敗することを確かめてから直す
- **振る舞いを変えない修正**（リファクタ、パスの解決方法、コメント など）: テストが通ったまま直す
- 直すたびに、プロジェクトのテスト、型チェック、lint を実行する。コマンドはプロジェクトの CLAUDE.md に従う
- **1 件 = 1 コミット**。コミットメッセージは、プロジェクトのコミット規約に従う
- 直している途中で、指摘のとおりには直せないと分かった場合は、変更を取り消してその指摘を止め、理由を添えてユーザーに判断を仰ぐ。ほかの指摘は続けてよい
- 指摘の範囲を超える修正は行わない。気づいたことは報告に回す

### 5. 判断を記録する

「直さない」「後で直す」と決まった指摘について、スレッドへの返信の下書きを作る（例: 「対応しません: drizzle-kit は out を実行したディレクトリからの相対パスで扱うため」「第4章の signup で対応します」）。この返信があると、`/my-code-review` の再レビューで同じ指摘がくり返されない。

返信は Pending にならず、すぐに公開される。そのため、下書きを示してユーザーの承認を得てから投稿する。

```bash
gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies -f body='返信の本文'
```

Pending レビューのコメントには返信できない。その場合は、下書きだけを示し、レビューを提出した後に返信するようユーザーに伝える。

### 6. push して再レビューに渡す

1. push する
2. `/my-code-review {pr_number}` を実行して、再レビューを始める
3. 次の内容を報告して終わる。次の周を回すかどうかは、ユーザーが決める
   - 指摘ごとの結果（直した（コミット SHA）/ 直さない / 後で直す / 直せなかった（理由））
   - 実行したテスト、型チェック、lint の結果

## 注意事項

- PR のドラフトを解除しない（`gh pr ready` を実行しない）。マージもしない
- Pending のレビューは、ユーザーの下書きとして扱う。許可なく提出・削除しない
- プロジェクトの CLAUDE.md やフックに PR の運用ルールがある場合は、そちらを優先する
